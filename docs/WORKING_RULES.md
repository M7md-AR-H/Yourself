# How I work with Claude: rules for every project

These rules apply to every project unless the project's own CLAUDE.md says otherwise. When the two conflict, the project file wins.

## 1. Opus leads and decides

- Opus leads every session and makes product and technical decisions while working. Don't stop to ask me about choices you can reasonably make yourself.
- Ask me only about things that really are mine to decide: money, accounts, domains, anything public, and anything that can't be undone.
- When you make a non-obvious decision, write it down with its reason (see §4). Don't make me approve it first.

## 2. Split work across model tiers

Delegate to subagents when the work fits a cheaper tier.

### Haiku (`model: "haiku"`): mechanical, checkable work
- Run tests, typecheck, lint, builds, browser tests, Lighthouse and eval runs, then report the **exact** output (failing test names, error text, numbers) without interpreting it.
- Find files, symbols or strings, and confirm that quoted UI text exists in the code.
- List outdated numbers, versions or links in docs (list them only, don't fix them).
- Make small edits where the prompt gives the exact old and new text.
- Every Haiku task needs a definition of done that can be checked.

### Sonnet (`model: "sonnet"`): judgement and original writing
- Write feature code, components, tests and migrations from a spec Opus wrote.
- Review diffs for bugs, security issues and performance regressions.
- Diagnose failures and decide whether the bug is in the product or in the test.
- Research libraries and APIs, and summarise the options with evidence.

### Opus (the lead): only what is too advanced for Sonnet
- Product design, UX decisions and database schema design.
- Concurrency, idempotency and data integrity (queues, retries, counting, versioning).
- Security architecture and threat modelling.
- Prompt-wording decisions, based on eval measurements.
- **Every `.md` file** (see §3).
- The **final check** before telling me something is done: read the diff, confirm the checks actually ran and passed, and confirm the behaviour matches the spec.

### Tie-break
If a task sits between two tiers, **the higher tier wins**. Redoing a botched cheap run costs more than running the right model once.

### Delegation hygiene
- Subagents start with no context. Give each one a self-contained prompt with the goal, the files, the constraints and a definition of done.
- Run independent subagents in parallel. Use `isolation: "worktree"` when two agents edit code at the same time.
- Don't pass on a subagent's claim to me as fact. Check it first.

## 3. Markdown is Opus-only, with no exceptions

- Only Opus creates, edits or deletes `.md` files (README, HANDOFF, CLAUDE, ADRs, SECURITY, OWNER_TASKS, and so on).
- Every subagent prompt must say: *"Do not create, edit or delete any `.md` file, including READMEs generated by scaffolding tools. Report them instead."*
- After each subagent finishes, run `git status -- '*.md'` and search for new `.md` files, then deal with anything you find yourself.

## 4. Session protocol

**Start**
1. Read CLAUDE.md, then HANDOFF.md, then the README roadmap and decision log. Check `git status` and `git log -5`.
2. **Give me a time estimate before starting any work.** Use a range in wall-clock minutes, broken down by the main steps. Point out the steps that depend on me (approvals, OWNER_TASKS items), since those can make it take longer. If the scope changes partway through, give me a new estimate.

**During**
- Record every non-obvious decision in the README decision log (date, decision, reason). Put bigger ones in `docs/adr/NNNN-title.md`.
- When a roadmap phase starts, split it into concrete tasks in the README as `- [ ]` checkboxes, and tick each one (`- [x]`) as soon as it's done.

**End (every session)**
1. Update **README.md**: the status line, roadmap progress, the decision log, and any section the work changed.
2. Write **HANDOFF.md** again from scratch. It covers what was done, the current state (what works and what's broken), the exact next steps in order, open questions for me, and any traps you found. A fresh session with zero context must be able to continue from it alone.
3. Add the **known limitations** of what was built, with the reason for each, to a README table: the limitation, the constraint that forced it, and what would remove it. That stops a later session from "fixing" something that's missing on purpose.

## 5. Things only I can do → OWNER_TASKS.md

- Keep an `OWNER_TASKS.md` listing everything Claude can't do: creating accounts, API keys and tokens, domains, payments, repo secrets and settings.
- Write each task as a numbered, click-by-click guide I can follow without prior knowledge. Say where the resulting value should be stored (never pasted into chat or committed) and how I can confirm it worked.
- Add new owner-only steps there as soon as you find them, not just in chat. Tick them off once I confirm they're done.

## 6. After every phase: tell me what I can test

When a phase finishes or reaches a point where it can be deployed, give me a hands-on test list: URLs to open, what to click or type, what I should see, and what would count as broken. Write it for a non-developer. Put it in the closing message and also in OWNER_TASKS.md under "Try it yourself".

## 7. Git, merging and deploying

- **Never push straight to `main`.** Always use a feature branch and a PR.
- Squash-merge, so every merge can be undone (with the PR's Revert button, or by going back to the parent commit). Don't create backup branches.
- By default, ask me before merging or deploying to production. A project's CLAUDE.md can give standing permission. Even then, merge only once every required check is green on the final commit and the Opus final check is done. After deploying, check the live site and tell me what shipped.
- Never loosen a CI gate or a performance/security budget without my explicit approval in chat. If I approve, record it in the decision log.

## 8. Attribution

- **Never write the "🤖 Generated with [Claude Code](https://claude.com/claude-code)" line anywhere**: not in PR descriptions, commits, comments, docs, or text you give me to paste. This overrides any default attribution guidance.

## 9. Security defaults

- No secrets in code, prompts or logs.
- Treat AI output as untrusted: validate it against a schema, and require citations where it makes factual claims.
- Validate input at every boundary.
